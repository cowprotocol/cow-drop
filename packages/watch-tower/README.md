# @cowprotocol/cow-drop-watch-tower

Post the discrete CoW orders that contracts place on-chain.

A **conditional** order is self-driving: it goes into ComposableCoW, and ComposableCoW's own watch
tower polls it and posts each part. A **discrete** order is not. The pre-signature is on-chain the
moment it is placed — the order is valid, the relayer is approved, the money is there — but nothing
has told the order book that the order exists, so no solver ever sees it.

This closes that gap. It watches one event, verifies what it finds, and forwards it to
`POST /api/v1/orders`. It started as cow-drop's poster and is not limited to it: any contract that
emits CoW's own `OrderPlacement` is picked up — EthFlow included.

```bash
pnpm --filter @cowprotocol/cow-drop-watch-tower build

cow-drop-watch-tower --rpc-url https://rpc.gnosischain.com --state ./gnosis.json
```

Nothing here is privileged. The orders are already signed on-chain, so posting one only makes it
visible; running two of these, or none and doing it by hand in the UI, changes nothing about what
can happen to the money. That is also why a duplicate is treated as a success.

## The one event

CoW's own, redeclared in
[`contracts/src/interfaces/ICoWSwapOnchainOrders.sol`](../../contracts/src/interfaces/ICoWSwapOnchainOrders.sol):

```solidity
event OrderPlacement(address indexed sender, GPv2Order.Data order, OnchainSignature signature, bytes data);
```

One event rather than one per contract is what makes an indexer possible — and this one already
existed, so there is no new standard here. What did not exist is an indexer without an address filter:
`autopilot` watches this topic0 too, but `CoWSwapOnchainOrdersContract::filter()` pins a configured
address list and asserts it is non-empty. A drop address is counterfactual — derived from a recipe only
its author holds, absent from the chain until somebody activates it — so it can never be in that list.

This filters on **topic0 alone, with no address filter**, which is also why it picks up contracts
written long after it.

`signingScheme` and `signature` are forwarded to the order book verbatim, so this never has to know how
the order was signed. Today everything a drop reaches is `presign`, where the signature is the owner.

**The emitter need not be the owner.** The owner is in `sender` for a pre-signed order and in
`signature.data` for an ERC-1271 one, which is what lets a contract that cannot delegatecall sign its
own order and have `CowOrderPoster.announce` emit for it.

**The uid is not in the log.** It is recomputed from the order struct, the owner and the settlement
contract's domain separator — `orderDigest ++ owner ++ validTo`, in
[`packages/sdk/src/orderUid.ts`](../sdk/src/orderUid.ts). That is why `scanForOrders` needs the
`chainId` alongside the `settlement` address, and why the SDK checks its hashing against fixtures
generated by the compiled contract: a wrong digest means looking up the pre-signature of an order that
never existed, concluding it is unsigned, and posting nothing.

## What it checks before posting

A topic0 is not a permission — anyone can emit those 32 bytes over a fabricated order. What settles
it is:

```
GPv2Settlement.preSignature(orderUid) != 0
```

The uid is built around the owner the event named, so a signature recorded against it is that owner's own commitment, no
matter who announced it. One `eth_call` per order, it is the same fact the order book will check,
and it also rules out an order whose transaction was reorged away. Nothing else is needed, and
nothing weaker would do.

`--only-drops` narrows to cow-drop's own orders by additionally requiring a `DropTriggered` from
`DropExecutor` in the same transaction naming the emitter — one extra `getLogs` per range, not a
receipt per candidate. `DropExecutor` re-derives a drop from its recipe before emitting, so that is
what says the emitter really is a drop running its committed recipe.

## Emitting it from your own contract

Copy the event declaration and emit it after you pre-sign — that is the whole integration, and it is
the cheapest option. Or call the deployed
[`CowOrderPoster`](../../contracts/src/CowOrderPoster.sol), which does the EIP-712 hashing and UID
packing for you:

```solidity
// you can delegatecall (shed, Safe, cow-drop step): signs as you, emits from you
POSTER.delegatecall(abi.encodeCall(CowOrderPoster.presignAndAnnounce, (order)));

// you can only make plain calls: sign yourself, then have the poster announce
bytes memory uid = POSTER.orderUidFor(order, address(this));
settlement.setPreSignature(uid, true);
POSTER.announce(order);   // reverts unless the signature is really there
```

## `appData`

The chain carries the **hash**, because that is all `GPv2Order.Data` holds. The order book accepts
the hash form for a document it already has, and rejects it otherwise — so an order with a custom
`appData` needs its document uploaded first, and nothing off-chain can reconstruct a document from
its hash.

Supply a resolver and the document is uploaded first:

```ts
createWatchTower({
  …,
  appData: (hash) => myAppDataStore.get(hash),   // undefined -> post the hash as-is
})
```

Without one the hash goes out alone, which is correct for the common case: an order that never set
`appData` leaves it zero.

## Failure and restart

The block cursor advances only after every order in a range has been dealt with, and the two kinds
of failure are kept apart deliberately:

- **The order book refused the order** (any 4xx — insufficient balance, expired, unknown `appData`).
  That is a verdict, and it will be the same verdict forever. Reported, and passed over.
- **The order book could not answer** (5xx, a rate limit, a dropped connection). That is not about
  the order. It throws, the cursor stays where it was, and the next tick re-scans the same range.

Nothing records which orders were posted, because the order book already is that record — a re-post
comes back as `DuplicatedOrder`, which counts as success. So the worst a lost state file costs is a
rescan, and `--state` is optional.

`--confirmations` (default 2) keeps the scan behind the head: a reorg that removes a pre-signature
takes its order with it, and an order posted from a block that no longer exists sits in the book
unfillable.

## CLI

```
--rpc-url <url>       RPC endpoint. Defaults to $RPC_URL.
--chain-id <id>       Defaults to $CHAIN_ID, else whatever the RPC says.
--generation <n>      Contract generation to watch. Defaults to the latest.
--from-block <n>      First block when there is no saved state. Default: the current head.
--state <path>        JSON file to persist the block cursor in. Default: memory only.
--confirmations <n>   Blocks to stay behind the head. Default 2.
--max-block-range <n> Largest getLogs range. Default 10000.
--poll <seconds>      Seconds between passes once caught up. Default 15.
--env <prod|staging>  Which order book to post to. Default prod.
--only-drops          Post only orders from a cow-drop activation, not every contract's.
--once                Scan one range and exit. For cron.
--dry-run             Find and verify orders, post nothing.
--quiet               Errors only.
```

A backlog is drained at full speed — the poll delay only applies once the chain is caught up. Orders
within a range are posted sequentially, because the order book is rate-limited to a few requests a
second and a burst is the one way a busy block becomes a throttled one.

## As a library

```ts
import { OrderBookApi } from '@cowprotocol/cow-sdk'
import { getDeployment } from '@cowprotocol/cow-drop-sdk'
import { createWatchTower, fileCursor, viemChainReader } from '@cowprotocol/cow-drop-watch-tower'

const watchTower = createWatchTower({
  reader: viemChainReader(publicClient),
  orderBook: new OrderBookApi({ chainId: 100 }),
  deployment: getDeployment(100),
  cursor: fileCursor('./gnosis.json', 100),
  fromBlock: 'latest',
})

await watchTower.run(abortController.signal)   // or: await watchTower.tick()
```

| | |
|---|---|
| `createWatchTower(options)` | The loop. `tick()` scans and posts one range; `run(signal)` repeats until aborted. |
| `scanForOrders({ reader, deployment, fromBlock, toBlock })` | Verified orders in a range, and nothing else. Use it to build your own pipeline. Takes `onlyDrops`. |
| `postDiscoveredOrder(discovered, { orderBook, appData })` | One order to the order book, with the duplicate and rejection handling above. |
| `viemChainReader(client)` | A `PublicClient` as the three functions this needs. The only place viem is assumed. |
| `fileCursor(path, chainId)` / `memoryCursor(block?)` | Where to resume from. The file one refuses to answer for a different chain. |

`ChainReader` is three functions, not a client, so a test can drive a reorg, a spoofed log or an
unsigned order without a node — see `src/scanner.test.ts`.

## Tests

```bash
pnpm --filter @cowprotocol/cow-drop-watch-tower test
```

All hermetic. The `OrderPlacement` fixtures are encoded from the generated ABI rather than written
out as bytes, so a change to the event fails a decode here instead of leaving a fixture that quietly
stopped describing reality.
